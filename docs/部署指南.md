# Docker Compose 部署指南

> 一条命令起全栈：`docker compose up -d --build`
> 前提：目标机器已装 Docker Engine + Compose v2（`docker compose version` 能出结果）

## 一、架构总览

```
                     服务器 211.101.246.225
公网 ──> :8088 ──┐
                  ▼
          ┌───────────────┐
          │ web (nginx)   │  静态文件 dist/
          │  /            │  + SPA history 路由兜底
          │  /api/    ────┼──┐
          │  /uploads/ ───┼──┤ 反代（compose 内网 DNS）
          └───────────────┘  │
                             ▼
                    ┌───────────────┐
                    │ server (go)   │  :8080，非 root 运行
                    └──┬─────────┬──┘
                       │         │
                ┌──────▼──┐  ┌───▼─────┐
                │ mysql   │  │ redis   │   ← 都不映射宿主端口，
                │ :3306   │  │ :6379   │     仅 compose 内网可达
                └─────────┘  └─────────┘

  数据: ./data/{mysql,redis,uploads}（bind mount，跟着项目目录走，备份一个目录带走全部）
```

**为什么这样设计：**

| 决策 | 原因 |
|------|------|
| MySQL/Redis 不映射宿主端口 | 服务器上已有实例占着 3306/6379；数据库不对公网暴露，少一个攻击面 |
| Nginx 同源反代 `/api`、`/uploads` | 浏览器只看到一个 origin，**CORS 问题整个消失**（后端那套 CORS 中间件只服务开发期） |
| 服务名互访（`mysql:3306`、`http://server:8080`） | Docker 内置 DNS；容器重启换 IP 无需改配置 |
| `depends_on: service_healthy` | Go 服务等 MySQL 真正能响应才启动，避免连接被拒 panic 退出 |
| 数据 bind mount 到 `./data/` | 数据跟着项目目录走：备份/迁移 `/www/home-items` 一个目录带走全部；`docker compose down` 甚至重建镜像，数据都在 |
| init.sql 挂到 `/docker-entrypoint-initdb.d/` | 首次初始化自动建库建表 + 种子账号（密码沿用 Admin@123456 等） |

## 二、首次部署（从 Windows 本机到服务器）

### 1. 打包（排除 node_modules / dist / 上传的图片）

```powershell
cd D:\personal\test-db
tar --exclude node_modules --exclude dist --exclude .git --exclude server/uploads -czf ../home-items.tar.gz .
```

（Windows 11 自带 bsdtar；`--exclude` 对目录名全局生效。`.env` **不排除**——服务器上 compose 靠它）

### 2. 上传 + 启动

```powershell
scp ../home-items.tar.gz root@211.101.246.225:/www/

ssh root@211.101.246.225
mkdir -p /www/home-items
tar xzf /www/home-items.tar.gz -C /www/home-items
cd /www/home-items
docker compose up -d --build
```

> **存储位置说明**：这台服务器的 Docker `data-root` 已配置为 `/www/docker`
> （见 `/etc/docker/daemon.json`）——镜像、named volume 全部落在外接盘，
> 系统盘只承担 `/www/home-items` 的项目源码本身（约 123KB）。

首次 build 需要拉基础镜像 + 编译，预计几分钟。起来后：

```bash
docker compose ps          # 四个容器都应是 healthy/running
docker compose logs -f server   # 看到 Gin 的路由表即成功
```

浏览器访问 `http://211.101.246.225:8088`，用 `admin / Admin@123456` 登录。

### 3. 防火墙放行（如果访问不通）

```bash
# 服务器上确认监听
ss -tlnp | grep 8088
# 云厂商安全组也要放行 8088/TCP 入方向
```

## 三、日常操作

| 场景 | 命令 |
|------|------|
| 改了代码，重新部署 | 本地重新 tar/scp 覆盖后：`docker compose up -d --build`（只重建变化的镜像，数据库不动） |
| 看后端日志 | `docker compose logs -f server` |
| 进 MySQL 排查 | `docker compose exec mysql mysql -uroot -p home_items` |
| 进 Redis 排查 | `docker compose exec redis redis-cli -a "$REDIS_PASSWORD"` |
| 重启某个服务 | `docker compose restart server` |
| 全部停掉（保留数据） | `docker compose down` |
| **清空一切（删库！）** | `docker compose down && rm -rf data/mysql data/redis data/uploads` |

## 四、原理速讲

### 4.1 多阶段构建为什么镜像小 40 倍

`server/Dockerfile` 两个阶段：阶段 1 用 `golang:1.26-alpine`（带完整工具链，~800MB）编译出**一个静态二进制**（`CGO_ENABLED=0` → 不动态链接 libc）；阶段 2 的 `alpine:3.22`（~8MB）只 `COPY` 这个二进制。编译工具链被丢在阶段 1，不进最终镜像。

### 4.2 层缓存：改代码为什么不用重新下依赖

Dockerfile 每条指令一层，按序缓存命中。依赖清单（`go.mod go.sum` / `package-lock.json`）单独一层：

```
COPY go.mod go.sum ./     ← 没变
RUN go mod download       ← 直接命中缓存，秒过
COPY . .                  ← 变了，从这里开始重建
```

### 4.3 named volume vs bind mount：为什么本项目用后者，以及权限坑

两种持久化方式的差异：

| | named volume | bind mount（本项目采用） |
|---|---|---|
| 存储位置 | `/var/lib/docker/volumes/`（本机即 `/www/docker/volumes/`） | 项目目录下 `./data/`，肉眼可见 |
| 首次挂载 | 把**镜像内该路径的内容和属主复制进卷**（"首次复制"行为） | **什么都不做**，宿主机目录原样透进容器 |
| 备份/迁移 | 要知道 Docker 内部路径 | 备份项目目录即备份全部 |
| 生命周期 | `docker compose down -v` 一并删除 | 与 Docker 无关，`rm -rf` 手动管理 |

**权限坑**（本项目实测踩过）：server 容器以非 root 的 `app(10001)` 运行，Dockerfile 里 `chown app:app` 的功劳只对 named volume 有效；换 bind mount 后必须在宿主机预置：

```bash
mkdir -p data/uploads && chown 10001:10001 data/uploads   # 否则上传图片全 permission denied
```

MySQL/Redis 无需手动 chown——官方镜像的 entrypoint 以 root 起手，初始化时会自动 `chown` 数据目录再降权运行。

### 4.4 `$$` 转义是什么意思

compose 里 `${VAR}` 在**部署机上**被 `.env` 替换；`$$VAR` 是转义，让 `$` 原样传进容器、由**容器内** shell 展开。healthcheck 里 `-p$$MYSQL_ROOT_PASSWORD` 用的是容器自己的环境变量（MySQL 镜像确实设置了它）。

### 4.5 同源反代如何"消灭"CORS

开发期：浏览器在 `:5173`，API 在 `:8080` —— 端口不同即跨源，需要 CORS 头 + `withCredentials` + Cookie SameSite 精心配置。

生产期：Nginx 把 `/api/`、`/uploads/` 转发到 server，浏览器全程只跟 `:8088` 一个 origin 打交道 —— 没有跨源，CORS 协议根本不触发。refresh token 的 httpOnly Cookie（`Path=/api/v1/auth`、`SameSite=Lax`）在同源下天然工作。

### 4.6 时区一致性

DSN 里 `loc=Local` + `DATETIME` 全按本地时区读写。三个容器统一 `TZ=Asia/Shanghai`，server 镜像装了 `tzdata`。**漏掉任何一个**，录入时间就会差 8 小时——这是容器化 MySQL 应用最常见的坑。

## 五、常见坑

1. **改了 `sql/init.sql` 但重启后没生效** —— init 脚本只在 `data/mysql` 为空时执行。想重跑：`docker compose down && rm -rf data/mysql && docker compose up -d`（清库，种子重建）。
2. **`docker compose up` 后 server 反复重启** —— 大概率 MySQL 还没就绪；看 `docker compose logs mysql`。healthcheck 已配置 `start_period: 60s`，一般不会出现。
3. **上传图片 413** —— Nginx `client_max_body_size 6m` 和后端 `MAX_UPLOAD_MB=5` 是两道独立的限制，都要过。
4. **想上 HTTPS** —— 前面再加一层（云 LB 或 Caddy/Nginx 做 TLS 终止），然后把 server 的 `COOKIE_SECURE` 改 `"true"`。
5. **国内服务器 build 卡在拉镜像** —— Dockerfile 里已给 GOPROXY/npm 镜像；基础镜像拉不动需自配 registry mirror（`/etc/docker/daemon.json`）。
